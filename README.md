# 税收政策 RAG 检索质量与评测系统

> 面向中文税收政策，把检索从「能跑」做到「**说得清好在哪、差在哪**」。
>
> 大多数 RAG 项目停在能跑：接个向量库、调个 embedding、拼个 prompt。本项目把「换个切分会不会更好」
> 「加重排值不值那几百毫秒」变成**可复现的数字**——每个结论都有基线对照、有成本口径。

---

## 项目要解决的问题

企业财税场景下，政策检索有三条硬约束：

1. **政策会过期**。「设备器具一次性扣除」优惠有执行期限，过期政策不能作为依据。
2. **术语字面不重合**。用户问「小微企业所得税」，文件写「小型微利企业」，纯关键词检索召不回。
3. **答案必须可溯源**。说不出「依据哪份文件的第几条」，回答就没有意义。

这不是「做个知识库问答」——是怎么**量化地**知道检索够不够用。

## 数据

| | |
|---|---|

## 评测结果

> 360 条 query，金标 doc 级。全部数字由 `python scripts/04_run_ablation.py` 实测产出，
> 同一命令可复现。原始结果见 `reports/ablation.json`。

| 配置 | Recall@1 | Recall@3 | MRR | nDCG@3 | P@3 | 延迟 p50 | API/query |
|---|---|---|---|---|---|---|---|
| ① 基线：固定切分 + 纯向量 + 不重排 | 58.6% | 84.2% | 0.705 | 0.740 | 41.3% | 0.29s | 1 |
| ② 换递归切分 | 60.6% | 83.6% | 0.713 | 0.745 | 35.7% | 0.29s | 1 |
| ③ 换条款切分 | 64.2% | 88.9% | 0.755 | 0.789 | 41.8% | 0.30s | 1 |
| ④ 条款切分 + 纯 BM25 | 61.9% | 83.6% | 0.715 | 0.746 | 39.0% | **0.06s** | **0** |
| ⑤ 条款切分 + 混合召回 | **67.2%** | 89.2% | **0.770** | **0.802** | **42.7%** | 0.36s | 1 |
| ⑥ 条款切分 + 纯向量 + 重排 | 64.2% | 90.8% | 0.760 | 0.798 | 42.0% | 0.78s | 2 |
| ⑦ 全量：条款切分 + 混合召回 + 重排 | 62.8% | **91.1%** | 0.756 | 0.796 | 42.0% | 0.86s | 2 |

### 三个结论，两个反直觉

**1. 领域感知切分确实有效，但"递归切分"完全无效。**

条款切分把 Recall@3 从 84.2% 拉到 88.9%（+4.7pp），Recall@1 从 58.6% 拉到 64.2%（+5.6pp），
**且不增加任何成本**。而递归切分（LangChain 的默认思路）几乎等于固定切分（83.6% vs 84.2%）。

这与已有研究的结论一致——arXiv 2410.13070 实测"复杂切分在真实文档上常打不过简单切分"。
但本项目的**条款切分**不是"更复杂的通用切分"，
它是**利用了领域的结构**（政策文本天然有「一、二、」条款边界）。
**通用复杂度无收益，领域知识有收益**——这个区分才是重点。

**2. 重排不是白给的：它提升 Recall@3，却拉低 Recall@1。**

重排让 Recall@3 从 89.2% 升到 91.1%（+1.9pp），但 Recall@1 从 67.2% **降到** 62.8%（-4.4pp），
MRR 也从 0.770 降到 0.756。代价是延迟从 0.36s 涨到 0.86s（2.4 倍），API 调用翻倍。

**怎么解释**：交叉编码精排的"相关性"打分，和"这份文件就是唯一正确答案"并不完全一致。
它擅长把相关内容都捞进窗口（Recall@k 上升），
但有时会把真正的答案从第一位挤下去（Recall@1 下降）。

**所以该不该上重排，取决于下游怎么用**：
下游是"读 top-3 综合判断"就用重排；下游是"直接用 top-1"就别用。
**这不是"重排好不好"，是一个有明确条件的取舍。**

**3. 纯 BM25 是被低估的基线：零 API 调用，0.06 秒，Recall@3 就有 83.6%。**

比向量检索低 5.3pp，但**不花一分钱、不依赖网络**。
对成本敏感的离线场景，"BM25 打底 + 向量补充"可能是更划算的结构。

### 失败样本（32/360，8.9%）

失败集中在两类，都不是"检索算法不行"，而是**任务本身要求的粒度不匹配**：

1. **"资格名单"类问题**。问"某慈善组织有没有捐赠税前扣除资格"，
   金标是当年的《公益性社会组织捐赠税前扣除资格名单》公告，
   但检索到的是**通用政策**（"公益性捐赠税前扣除有关事项的公告"）。
   通用政策确实相关，但回答不了"这一家有没有"——**需要的是名单，不是规则**。
2. **版本时效类问题**。问"某免税政策到什么时候结束"，
   金标是**最新一版**延续公告，检索到的却是前几版的旧通知。

这两类的共同点：**答案在"哪一份"里，而不在"哪段话"里**。
对应的改进方向不是调切分或换模型，而是——
在检索层加上**文档级元数据的硬过滤**（发文年份、文号版本、文档类型）。
这也是把检索从"文本匹配"升级为"结构化查询"的接口。

---

### 生成层：忠实度 0.986，但它骗不了人

用另一个 LLM 当裁判，判断答案是否被检索片段支撑（`scripts/06_eval_generation.py`，60 条抽样）：

| 指标 | 值 |
|---|---|
| 忠实度均值 | **0.986** |
| 有依据比例 | 96.7% |
| 拒答率 | **0.0%** |
| 无依据且未拒答 | 2 条 |

**这个 0.986 不能单独看。** 拒答率 0% 才是关键：

在这 60 条里，检索层有约 9% 的题没找对文档，但模型**照样基于错误上下文自信作答**，
而裁判只检查「答案是否忠实于给出的片段」，不检查「给出的是不是对的那份政策」。

**忠实度高 + 检索不完美 = 自信的错误答案。** 这是 RAG 最危险的失效模式：
答案格式完整、引用齐备、读起来毫无破绽，但依据本身就是错的。

所以本项目的结论是：

> **忠实度只能证明"没瞎编"，不能证明"答对了"。**
> 要判断答得对不对，必须回到检索层的 Recall/MRR。

这也解释了为什么本项目的重心放在检索评测上——
生成层的指标再漂亮，也兜不住检索层的窟窿。

**2 条无依据样本**（需人工复核，LLM 裁判本身有噪声）：模型从片段里读到了文号，
但把附件里的具体细则当成了正文结论，属于「引用正确、推断越界」。

## 运维与回归

### 索引增量更新

政策是持续发布的。一份新公告落库后，全量重建要把几千条片段重新切分、重新 embed；
增量更新只处理变化的那几条。

```bash
python scripts/07_update_index.py --dry-run   # 只看差异
python scripts/07_update_index.py             # 实际更新
```

差异以 `data/processed/corpus.jsonl` 为准：语料有索引没有 → 新增；索引有语料没有 → 移除。

**两个容易搞错的点**：

1. **每次更新的开销不在 embed，在向量矩阵重建**（`np.vstack`）。所以**攒一批一起更**比来一条更一次划算。
2. **政策到期 ≠ 从索引里删掉**。到期应由检索层的 `valid_to` 过滤——
   过期政策依然有历史检索价值（用户可能在问历史年度的事）。
   从索引删除只针对"语料里真的没有了"的情况。

### 回归评测

改一处切分逻辑、调一个分块参数——单元测试全绿，但**检索质量可能已经掉了 5 个点**，
而你不会知道。所以要有回归基线：

```bash
python scripts/08_regression.py --save-baseline   # 首次存基线
python scripts/08_regression.py                   # 之后对比，退化则退出码非 0
```

盯三样东西：

| 盯什么 | 怎么判 |
|---|---|
| 指标基线 | Recall@k / MRR / nDCG 掉超过 2 个百分点即失败 |
| 已知失败样本 | 那批"已知召不回"的题如果变了（变好或变差）都要有人看一眼，说明行为变了 |
| 延迟 | p50 一并记录，防止用延迟换指标 |

容差取 2 个百分点而不是 0：embedding 接口本身有微小波动，
但也不能大到掩盖真实退化。

## 核心设计取舍

详见 [docs/DESIGN.md](docs/DESIGN.md)。几条最值得说的：

- **切分不做预设结论**。领域感知的条款切分看起来更对，但已有研究实测复杂切分在真实文档上常打不过简单切分（arXiv 2410.13070）。所以本项目**跑数据说话**，`article` 到底值多少分由消融给出。
- **混合检索用 RRF 而非加权求和**。向量分是余弦相似度、BM25 分是无界实数，量纲不同，加权需要一个没有理论依据的系数；RRF 只看名次，天然规避。
- **指标先截断再去重**。同一份政策占两个名额意味着挤掉了另一个可能相关的政策，这个代价必须体现——这个 bug 是被单元测试抓出来的（见 `tests/test_metrics.py`）。
- **拒答优于硬答**。重排分低于阈值直接回「依据不足」，堵死 RAG 最常见的翻车方式。
- **成本与效果一起报**。每条结论同时给延迟（p50/p95）与 API 调用次数，否则说不出「值不值」。

## 已知局限

主动写出来，比被问出来好：

1. 合成评测集偏「可直接查到」，真实提问更模糊，**指标会偏乐观**。
2. LLM 裁判有噪声，忠实度分数只作参考，需人工抽样校准。
3. 未覆盖跨文件多跳问题（「同时满足 A 和 B 时怎么组合」）。
4. 语料是抓取快照，不追增量更新。
5. 只用了 bge-m3 一种 embedding，跨模型对比留作后续。
